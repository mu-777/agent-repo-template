# web-seo — 検索での発見と見え方を整える

ホスティング先(GitHub Pages / Cloudflare / その他)を問わず共通の手順。**ホスティング固有の差は「オリジン直下を持てるか」「配信される HTML は何枚か」の 2 つに集約される**ので、まずそこを確定させてから施策を選ぶ。

シェア画像(OGP)は [web-share-assets](../web-share-assets/SKILL.md)、公開作業そのものは [web-deploy](../web-deploy/SKILL.md)。

---

## 0. 着手前に切り分ける — 「発見」か「ランキング」か

**この 2 つは打ち手がまったく違う。混同したまま作業を始めない。**

```bash
# 未インデックス(発見の問題)か、インデックス済みだが順位が低い(ランキングの問題)か
# ブラウザで: site:<公開 URL>
curl -sI <公開 URL>                      # まず 200 が返るか
```

| 状態 | 打ち手 |
|---|---|
| `site:` で 0 件 = 未発見 | Search Console 登録 → URL 検査 → インデックス登録リクエスト(§5)。**コード側の施策より先にこれ** |
| インデックス済みだが指名検索でも出ない | ランキングの問題。オンページはほぼ効かない。**被リンクとコンテンツの問題**(§6) |
| 出るが表示が変(サイト名・タイトル・アイコン) | 見え方の問題(§4)。原因ごとに別の対処 |

**「SEO 対策をして」への回答を、オンページ施策の羅列で終わらせない。** 3 つのどれで詰まっているかを先に実測し、効かない施策は「効かない」と言う。

## 1. 配信構成を確定させる(以降の可否がここで決まる)

先に 3 つを確認する。**これを飛ばすと「置いたのに効かないファイル」を作る。**

| 確認すること | 調べ方 | 効いてくるところ |
|---|---|---|
| **オリジン直下(`https://host/`)を自分で持てるか** | 配信先がサブパス(`host/project/`)かルートか | robots.txt の可否(§3)・サイト名の設定可否(§4) |
| **配信される HTML は 1 枚か、URL ごとに違うか** | SPA か、静的生成 / SSR か | canonical・hreflang・`<title>` を焼き込めるか(§2) |
| **ベースパス** | ビルド設定の `base` | 全リンク・sitemap・canonical の絶対 URL |

**「200 が返る = 機能している」ではない。** クローラや外部サービスが規約に基づいて取りに来るファイル(robots.txt / sitemap.xml / IndexNow キー / `.well-known`)は、**配信確認とは別に「仕様上そのパスを読みに来るか」を一次情報で確認する。**

## 2. `<head>` に入れるもの

### 全構成に共通

- **`<title>`** — 60 字目安(超過分は末尾から切られる)。**ブランドを先頭**に置き、区切りは**ダッシュ**(パイプは剥がされやすい)。ページごとに違う値にする。
- **`<meta name="description">`** — 検索スニペット用。**SNS 用のタグライン(`og:description`)とはキーを分ける。** タグラインは画像の帯に載る等の字数制約を抱えていることが多く、検索向けのジャンル語を入れる余地がない。役割が違うものを 1 つの文字列で兼ねさせない。
- **`<html lang>` / `og:locale`** — **実際に表示している言語と一致させる。** 中身が日本語なのに `lang="en"` のような食い違いは、タイトル書き換えの引き金になる(§4)。
- **`<link rel="canonical">`** — 末尾スラッシュ・クエリ違いの重複を正規化する。
- **`<meta name="robots">`** — 既定と同じでも意図の明示として置いてよい。**ページ単位で確実に効く**ので、サブパス配信でクロール制御が要るときは robots.txt ではなくこちら。
- **構造化データ(JSON-LD)** — アプリなら `WebApplication`(無料なら `offers.price: "0"`)、**サイト名を主張するなら `WebSite`**(§4)。**本文と食い違う内容を書かない。**
- **ファビコン** — 検索結果に出したいなら**ラスタ形式が要る**。詳細と生成は [web-share-assets](../web-share-assets/SKILL.md)。

### 多言語なら

- **hreflang は自分自身を含めて全言語版 + `x-default` を列挙し、双方向に指し合わせる**(片側だけだと無視される)。
- 出す場所は HTML の `<link rel="alternate">` / HTTP `Link:` ヘッダ / sitemap の `xhtml:link` の 3 方式が等価。**SPA で実行時注入する場合はクロールされる保証が一次情報で確認できていないので、sitemap 側にも同じ情報を冗長化しておく。**

### SPA(配信される HTML が 1 枚)の場合

- **ページごとに値が違うもの(`title` / `description` / canonical / hreflang / `og:url`)を `index.html` に焼き込まない。** どの URL に来ても同じ値を主張することになり、JS を実行しない相手には嘘になる。**実行時に `<head>` を upsert する層を 1 か所作り、そこに集約する。**
- 逆に、**言語が定まる前の既定値**(サイト共通の `og:image` / ブランド文言)はビルド時の静的タグでよい。**クローラは JS を実行しないので、SNS カードに出したいものは静的側に置く**([web-share-assets](../web-share-assets/SKILL.md))。
- **JS 無しで読む相手に本文が届かない。** `<noscript>` に実アプリと一致する要約を置く。**JS 有効時にブラウザが消してくれるのでクローキングにならず、ちらつきも出ない。**
- **常時 DOM に置く隠しテキスト(`sr-only`)は慎重に。** アクセシビリティ上必要な見出し(`h1`)なら妥当だが、**表示と違う文言を隠す形にしない。**
- **404 相当の画面(存在しない ID など)は自己申告で `noindex`。** そのとき**画面遷移で必ず外れること**を保証する(残ると正常なページまで検索から消える)。
- **アプリがレンダリング後に fetch するデータの置き場を robots.txt でブロックしない。** レンダリング用のクローラがそこを取れず、中身の無いページとして扱われる。

## 3. sitemap.xml と robots.txt — スコープ規則が正反対

**「サブパスだから無理」と一括りにしない。ファイルごとに規則が違う。**

| ファイル | オリジン直下を持てない場合 | 根拠 |
|---|---|---|
| **sitemap.xml** | **サブパスで有効。** ただし載せられる URL は**自分の置かれたディレクトリ配下だけ** | sitemaps.org のスコープ規則。Search Console から送信すれば発見も確実 |
| **robots.txt** | **無効。クローラはサブディレクトリの robots.txt を読まない**(origin + protocol + port 単位で `/robots.txt` 固定) | Google 公式 / RFC 9309 |
| **IndexNow キーファイル** | **サブパスで有効**(sitemap と同じスコープ規則)。Bing 系のみ・Google は非対応 | IndexNow 仕様 |

**robots.txt がオリジン直下に無いのは「不備」ではない。** 「robots.txt が無い = クロール制限なし」と解釈されるので、**404 のままが正しい設定**でありうる。**読まれないと分かっているファイルを「対応済み」の顔で置かない**(将来の自分を誤認させる負債)。置くなら「自動では読まれない」とファイル自身のコメントに書く。

**sitemap を書くときの注意:**

- **絶対 URL でしか成立しない。** 公開 URL がまだ決まっていない / ビルド時の環境変数が未設定なら、**作り話の URL で埋めず、sitemap 自体を生成しない**のが正しい挙動。
- 内容がビルド時の変数や日付に依存するなら、**コミットせずビルドで生成する**(生成物は gitignore)。
- **ページを増やしたら sitemap も増やす。** 手書きの一覧はルーティング定義と必ずずれるので、**同期漏れをテストか生成で機械的に守る**(レイヤ境界で自動化できないなら「両方直す」を地雷リストに 1 行)。

## 4. 検索結果の見え方 — 3 要素は原因も対処も別

検索結果は **サイト名 / タイトルリンク / ファビコン** の合成。「表示がおかしい」と言われたらどれかを特定してから直す。

| 症状 | 原因 | 対処 |
|---|---|---|
| **サイト名がホスティング事業者名になる** | ホスト名から推定されている。`og:site_name` だけでは弱い | **`WebSite` の JSON-LD を置く**(サイト名の最優先ソース)。**ただしサイト名はドメイン / サブドメイン単位で 1 つだけで、サブディレクトリには設定できない**(公式仕様)。サブパス配信で専用のサイト名が欲しいなら独自ドメインが唯一の手段 |
| **タイトルが本文中の別の見出しに書き換わる** | Google はタイトルを高頻度で書き換える。引き金は **`<h1>` と `<title>` の不一致**、**`<title>` の字系・言語が本文と一致しない**(日本語のページにラテン文字だけのタイトル等)、先頭ブランドが「サイト名的プレフィックス」と見なされる | `<h1>` を `<title>` に寄せる / **タイトルの言語を本文に合わせる** / 本文中にアプリ名が 1 度も出ないなら出す。**サイト名が採用されるとタイトルからブランドが省かれることがあるが、それは正常** |
| **ファビコンが既定アイコンになる** | 検索エンジンの**対応形式にベクターが入っていない**ことがある | ラスタ画像を併記する([web-share-assets](../web-share-assets/SKILL.md)) |

**この 3 つは、壊れていても画面上は何も変わらない。** ブラウザで見ても気づけないので、**「head に出ていること」をテストで守る**(該当タグが 1 つだけ存在する / HTML に直書きしていない)。

**反映には再クロールが要る(公式が「数日〜数週間」と明記)。** 直した当日に検索結果が変わらないことを「効いていない」と判断しない。急ぐなら Search Console の URL 検査からインデックス登録をリクエストする(§5)。

## 5. コードで完結しない作業(ユーザーに渡す)

**エージェントは実行できない。** 実装が終わったら、この手順を「あなたの操作が要ります」として報告に添える。

1. **Search Console にプロパティを登録し所有権を確認する。**
   - 確認方式は **`<head>` の meta タグが最も簡単**。**トークンをビルド時の環境変数にしない** — 手動デプロイなど一部の経路でタグが落ち、**所有権の確認が静かに外れる**(検索エンジンはタグが出続けていることを定期的に見に来る)。定数としてコードに置く(秘匿情報ではない)。
   - **HTML ファイル設置方式は、配信側が `.html` を落とすリダイレクトを返す構成だと失敗する**(検索エンジンはこの確認でリダイレクトを追わない)。
   - **ドメインプロパティは DNS TXT が要る**ので、他社のドメインの下に間借りしている構成では選べない。
2. **sitemap を送信する**(robots.txt の場所に依存せず登録できる)。
3. **URL 検査 → インデックス登録をリクエスト**(未発見・再クロールの最速手段)。
4. 必要なら Bing Webmaster Tools / IndexNow も同様に。

## 6. オンページで伸びなくなったとき

**「まだ足せるタグ」を探し始めたら、たいてい打ち止めのサイン。** ここから先の判断材料:

- **同型サイトの実例で裏を取る。** 題材ではなく**構成**(1 枚 canvas の可視化 / SPA / 静的ホスティング…)で似ているサイトを探す。**同一プロダクトの新旧・別ホスト版が併存していれば最良の対照実験**になる。**打ち手を提案する前に、その打ち手で実際に成功している同型サイトを 1 つ挙げる。挙げられないなら「効果は投機的」と明示する。**
- **狙うクエリの競合を調べる。** 既存の専門サイトに占拠されているクエリに同じ土俵で挑まない。**自分だけが持つデータに対応する空いているクエリ**を先に特定する。
- **リンク評価がどこから来るか確認する。** ソースホスティングからの被リンクは `rel="nofollow"` のことがある(実測できる: `curl -s <リポジトリ URL> | grep nofollow`)。その場合、**リポジトリの description / topics 整備は回遊には効くがリンク評価は 1 ミリも渡らない。**
- **恒久的な保守対象を増やす施策は、包括的な実施許可があっても着手前に確認する。** 判断軸は「**効果の確度 × ユーザーが背負う保守コスト**」。メタタグ追加(保守コストほぼゼロ)とランディングページ新設(文言の二重管理が恒久発生)は、同じ「SEO 対策」でも別物。**実験的に足すなら、最初から戻し方を設計しておく**(純静的・ビルド設定変更ゼロ・撤去手順を決定記録に)。

## やらないこと(逆戻りガード)

- **`<meta name="keywords">`** — 無視されるうえ乱用はスパム判定リスク。
- **SPA の `#root` に初期 HTML を差し込む** — マウント時に置換されて本文がちらつく。可読テキストは `<noscript>` に留める。
- **表示と違う隠しテキストを常時 DOM に置く。**
- **読まれない場所に置く robots.txt を「対応済み」として報告する。**
- **公開 URL が未定のまま絶対 URL を捏造する。**

- <https://developers.google.com/search/docs/appearance/favicon-in-search> — 検索結果のファビコンの対応形式
- <https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics> — レンダリング後の canonical を拾うこと / JS で入れるなら元の HTML と同じ値にすること

- RFC 9309(Robots Exclusion Protocol) — origin 単位で `/robots.txt` 固定
