# web-deploy — 公開の設定と、公開後にしか分からないこと

ホスティング先を問わず共通。検索での見え方は [web-seo](../web-seo/SKILL.md)、共有画像は [web-share-assets](../web-share-assets/SKILL.md)。

---

## 0. 前提の確認(毎回)

- **デプロイはユーザーの作業。エージェントは実行しない。** アカウント・API トークンはユーザーのもので、**公開は不可逆**(配った URL は消せない)。設定・ビルド・確認手順の用意までがこちらの仕事。
- **`main` / `master` への push = 本番公開**という構成が多い。**コミット・push は指示があったときだけ**というルールが、ここでは特に効く。
- **dev / preview サーバは立てない。** ビルドまでで止め、コマンドと URL を伝える。
- **公開 URL を決める値(プロジェクト名・ベースパス・リソース ID)は、公開後に変えるとリンクが死ぬ。** 保存済みのローカルデータ(`localStorage` の鍵)まで孤立することがある。**改名は「移行コードとセット」でしか提案しない。**

---

## 1. ビルド時の値と実行時の値

**静的ホスティングでは「環境変数」はすべてビルド時に焼き込まれる。** ここの取り違えが最も多い。

- **ホスティング側 / CI に変数を登録しただけでは配信物は変わらない。** 反映には**再ビルド**が要る。**デプロイのトリガに `workflow_dispatch` が無いと、変数を変えても次の push まで直らない**(定期ジョブ頼みだと最長で周期ぶん待つ)。触ったら「反映には再デプロイが要ります」と明示する。
- **どの値を変数にするかは「無いときに何が起きるか」で決める。**

| 値の性質 | 置き場 | 判断理由 |
|---|---|---|
| 秘匿情報(client secret / API キー) | **リポジトリに置かない。** gitignore 済みのローカルファイル + CI の secret から注入。`*.example` と手順書を用意 | 漏れると被害が出る |
| 秘匿ではないが環境ごとに違う(公開 URL・解析トークン) | CI の変数(build ステップだけが渡す) | ローカルビルドや E2E で本番の解析を汚さない。**この分岐を消さない** |
| 秘匿でなく、常に出ていないと困るもの(検索エンジンの所有権確認タグ) | **コードの定数**。変数にしない | 一部のデプロイ経路で落ちると**所有権の確認が静かに外れる**。しかも**落ちても画面は何も変わらないので気づけない** |

- **未設定時に作り話で埋めない。** 公開 URL が無いなら「sitemap を作らない・絶対 URL を出さない」が正しい挙動。
- **同じ事実を 2 か所に書かない**(実際に読み込む URL と、ドキュメントに書いた URL がずれると案内が嘘になる)。定数 1 か所を両方から読む。

## 2. ローカルとクリーンチェックアウトは違う

- **手元の作業ツリーは汚れている。「ローカルで通る」を CI が通る根拠にしない。** gitignore されたビルド生成物が手元にだけ残っていて、**クリーンチェックアウトでは存在しない**ことがある。再現するには生成物を消してから試す。
- **テストの中でサーバを立てるときは bind 先を `127.0.0.1` で明示する。** 既定の `localhost` は CI ランナーで IPv6 に解決されることがあり、**CI だけ**タイムアウトや `ECONNREFUSED` で落ちる。**ポーリング先と bind 先の表記を必ず揃える。**
- **フルの検証は CI の仕事。** ローカルは「今書いた変更が壊れていないか」を最短で見る範囲に絞る。**push 前にフルを流さず、push して CI に任せ、結果を見届けて赤ければ同じセッションで直す。** 何を流して何を流していないかは報告に必ず書く。

---

## 3. ホスティングの実挙動を仮定しない

**配信レイヤは自分のビルドの外側にあり、ローカルでは 1 つも再現しない。** 以下は初回デプロイで実際に壊れる典型。

- **事前圧縮(`.br` / `.gz`)は、配信側が自前で再圧縮する構成だと二重圧縮になって壊れる。** ブラウザは 1 回しか展開しないので、**生の圧縮バイト列がアプリに届く**(症状はパースエラー)。**配信側が `Content-Encoding` の指定を無視することがある** — ヘッダ設定ファイルの他の項目が効いていても、この項目だけ落ちる。**圧縮はホスティングに任せるのが既定。**
- **ヘッダ設定ファイルのルールは「より具体的なものが上書きする」とは限らない。** 当たったルールをすべて継承し、**同名ヘッダをカンマで連結する**実装がある(`Cache-Control` を 2 か所に書くと壊れる)。**同じヘッダを 2 つのルールに書かない。**
- **プラットフォームの既定を上書きしない。** HTML に `Cache-Control` を書かないのが正しいことがある(既定が既に正しい)。**書き足す前に既定値を一次情報で確認する。**
- **SPA のディープリンクは配信側の設定(404 フォールバック)で成立している。** 設定名と挙動を確認し、**変えたら実 URL で確かめる。**
- **URL 正規化のリダイレクト**(末尾スラッシュの付与・`.html` の除去)が既定で入ることがある。**リダイレクトを追わない外部サービス**(検索エンジンの所有権確認等)と組み合わさると失敗する。
- **ビルドツールの HTML 差し込みは「最初に見つかった閉じタグの手前」に入る。** コメントの中に閉じタグを文字どおり書くと、**スクリプトがコメント内に入って静かに読み込まれなくなる。**

## 4. 公開後にしか確認できないこと(初回は必ず打つ)

```bash
SITE=https://<公開 URL>

curl -sSI "$SITE/"                              # 200 か。Cache-Control が連結されていないか
curl -sSI "$SITE/<深いパス>"                     # SPA のディープリンクが 200 で返るか(404 でないか)
curl -sS --compressed "$SITE/<大きな静的データ>" | head -c 120   # 二重圧縮していないか(中身が読めるか)
curl -sS "$SITE/sitemap.xml" | head             # 生成されているか・絶対 URL か
curl -sS "$SITE/robots.txt"                     # 意図しない Disallow が無いか
curl -sS "$SITE/" | grep -o '<meta[^>]*>' | head -40   # head のタグが出ているか(解析・確認タグ・OGP)
```

**エージェントが確認できないもの**(報告に「実機確認待ち」と明記する):

- **SNS カードの実際の見え方**(クロップ・キャッシュ)。実投稿でしか分からない。
- **検索結果の見え方**。再クロール待ちで数日〜数週間かかる。
- **実機のフォント・DPI・OS のダークモード・ソフトキーボード。**
- **CDN キャッシュの実効**(パージのタイミング)。

## 5. アクセス解析を入れるとき

- **「プロキシしているサイトなら自動で入る」類の機能は、配信方式が違うと対象外**になる。**自動注入を当てにせず、スニペットを自分で差し込む。**
- **`index.html` に直書きしない。** ビルドの差し込み口(HTML 変換プラグイン)1 か所に集約する(OGP・確認タグと同じ場所)。
- **トークンが無いときは出さない分岐を必ず作る。** ローカルビルドと E2E で解析を汚さないためであり、**E2E が解析ドメインへの CORS 失敗をコンソールエラーとして拾って落ちる**実害もある。
- **SPA の画面遷移計測を切らない**(切ると最初の 1 画面しか数えられず、導入目的が消える)。
- **開示は実装とセット。** 外部送信の開示に要る最低限は「**送信される情報 → 送信先 → 利用目的**」の 3 つ。**1 つも削らない。** 保持期間などの**提供者側が予告なく変えられる数値を本文に書き写さない**。提供者の主張は「〜と表明しています」と帰属を付ける(運営者が検証できない事柄を断定しない)。
- **プライバシーポリシーに書く事実は実装から裏を取る**(何をローカル保存するか / 外部送信は何か / 広告の有無)。**送信先を足し引きしたらこのページも直す**(テストで縛れるとなお良い)。

## 6. デプロイ設定を触ったときの後始末

- **README には確定した手順のみ**(検討中・比較は書かない)。ユーザー向けの実行手順が長くなるなら、HTML の手順書を別に作る。
- **選択肢を比較して決めたこと**(ホスティング先・圧縮方式・解析ツール・ドメインの要否)は**決定記録に残す**。特に**不採用案とその理由**は逆戻りガードになる — 「転送量を詰めたい」で再訪しやすい領域。
- **CI の自動コミットは他のワークフローを起動しないことがある**(既定のトークンで作ったコミットが対象外)。**ジョブから別ジョブを直接呼ぶ**か、そのジョブの中で必要な検証を自分で回す。
- **壊れても画面が変わらないもの**(所有権確認タグ・サイト名の構造化データ・解析ビーコン)は、**必ずテストで守る。**
